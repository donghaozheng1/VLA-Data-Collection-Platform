# 07 · VLM 质检方案（数采工厂 · 内容合规质检）

> 面向第一阶段「数采工厂 / 数采作业」：**采集 → 质检 → 交付**，其中质检包含
> **结构质检**（已有 13 条规则）与本文档的 **VLM 内容质检**（新增）。
> 代码位置：`core/vlm_qc.py`（引擎）、`vlm_selftest.py`（自检）、
> `tools/vlm_mock_server.py`（离线 mock）、`tools/vlm_calibrate.py`（校准）。

---

## 1. 要解决什么问题

结构质检（`core/lerobot.py` 的 13 条规则）只能回答「**文件对不对**」：
行数是否等于视频帧数、有没有 NaN、时间戳是否单调、维度是否匹配……

但数采现场真正的坏样本是「**内容不对**」，文件层面完全正常：

| 现场真实情况 | 结构质检 | VLM 质检 |
| --- | --- | --- |
| 遥操人员没放成功，重采后**忘了删**失败的那条 | ✅ 通过（文件没问题） | ✅ 任务完成 → 末帧物体没到位 → 标记 |
| 物体中途掉落、捡起来重做 | ✅ 通过 | ✅ 动作成败 → 失败迹象 → 标记 |
| 有人从背景走过（不碰设备） | ✅ 通过 | ✅ 有人经过 → 标记 |
| 灯光突变 / 物体被碰动 / 设备异常 | ✅ 通过 | ✅ 开放世界事件 → 标记 |
| 同一条动作被重复采了两遍 | 内容级去重能查一部分 | ✅ 描述几乎一致 → 提示人工比对 |

**一句话**：结构质检保证数据「能用」，VLM 质检保证数据「合格」。

### 1.1 定位：语义级判断，与底层质检互补

VLM 质检是**独立环节**，与底层质检（结构规则 / lerobot-doctor 的 11 项）互补，
不重叠、不替代：

| | 底层质检 | VLM 语义质检 |
| --- | --- | --- |
| 回答的问题 | 文件**对不对**、分布**正不正常** | 画面里**到底发生了什么** |
| 手段 | 读 metadata / parquet / 解码抽检 | 抽帧拼图后问多模态模型 |
| 典型输出 | 行数≠视频帧数、时间戳回退、动作冻结 | 任务没执行完、动作失败、有人经过、意外事件 |
| 判据来源 | 阈值（可配置、可复现） | 模型判定（**正反问自一致**抵消 yes 偏置） |
| 能否触发打回 | 可以（`error`） | **永不**（只到 `warning`/`info`，交人复核） |

默认问题清单就是这 4 项语义级问题：

| # | 规则 | 问的是 | expect | 级别 |
| --- | --- | --- | --- | --- |
| 1 | `VLM·任务完成` | 任务动作是否执行完 | `yes` | warning |
| 2 | `VLM·动作成败` | 动作成功 / 失败判定 | `yes` | warning |
| 3 | `VLM·有人经过` | 有没有人经过（**动态路过也算**） | `no` | warning |
| 4 | `VLM·开放世界事件` | 开放世界事件检测（不预设类别） | `no` | info |

`expect` 表示"正向问法的合规答案"：`yes` 型是「是不是做到了」，`no` 型是「有没有出问题」。
第 3、4 项用 `no` —— **不能假设所有问题都以 yes 为合规**，否则清单里这些项
会被"无脑答 yes"的模型全部蒙混过关。

## 2. 两种 VLM 质检方式（都已实现，可单独跑也可同时跑）

### 方式一 `checklist` · 判别式（预设问题 + yes/no）

给 VLM 若干帧画面，逐条问：

> 该片段结束时，机器人是否已经完成了任务目标（物体已被抓取并放到指定位置或容器中）？

模型只回答 `yes / no` + 一句理由。**本质是一个二分类器。**

- 优点：输出确定、便宜、好算通过率、好校准（能算混淆矩阵）。
- 缺点：**只能查你想到的问题**；VLM 有「yes 偏置」（倾向答 yes）。

### 方式二 `describe` · 描述式（先描述 → 再判定）

不预设问题，先让 VLM 客观描述，再让它给结论：

> 请先用三句话客观描述：①初始状态 ②机器人做了哪些动作 ③结束状态。
> 然后判断任务是否完成、是否存在失败迹象。

输出的 JSON 契约（见 `core/vlm_qc.py::DESCRIBE_SCHEMA`）：

```json
{
  "description": "初始状态：… 动作：… 结束状态：…",
  "suggested_instruction": "把目标物体抓取并放到指定位置",
  "task_completed": true,
  "failure_signs": ["末帧目标物体未到位"],
  "verdict": "pass | fail | uncertain",
  "reason": "依据首末帧对比得出"
}
```

工程/学术上这叫 **caption-then-judge**，也叫 **VLM-as-a-judge**；
在质检语境下属于**零样本异常检测**（不预设缺陷类别）。

- 优点：**开放集**，能发现你没预设的问题（遮挡、异常光照、多余人手、重复采集）；
  判定有理由、可追溯；**描述文本顺带就是 VLA 的语言指令**。
- 缺点：输出有波动、成本更高、判定必须靠人复核。

### 为什么两个都做，而不是二选一

```
每条 episode
   │
   ├─ 第一级  checklist（闸门）   3~5 个预设问题 → 快、便宜、覆盖已知坏样本
   │
   └─ 第二级  describe（复核 + 标注）  描述 + 判定理由 → 开放集
                                       └→ suggested_instruction 回填成语言标注
```

两级是同一套代码，只是 prompt 与解析不同，配置里 `mode` 一改就切换。

### 「正反问自一致」——抵消 yes 偏置

VLM 容易无脑答 yes。所以每条问题都配一条**反向问法**，两问必须互相印证：

| 问题 | 合规时该答 |
| --- | --- |
| 是否**已经完成**任务目标？ | yes |
| 是否**尚未完成**任务目标？ | no |

两次答案矛盾 → 判为「**待人工确认**」（`info` 级），**不算不合规、不误报**。
这比调 temperature、换更大模型都便宜有效。

## 3. 怎么接进现有流水线

```
POST /api/jobs/qc  {dataset_id, vlm: true, vlm_mode, vlm_frames}
        │
        ▼
core/pipeline.py :: qc()                      ← 同一个任务处理器
        ├─ lerobot.check_episode()            ← 13 条结构规则（原有）
        └─ vlm_qc.run_episode_safe()          ← VLM 内容规则（新增）
                 │  抽帧 → 拼图 → 提问 → 解析 JSON
                 ▼
        qc_findings(rule="VLM·…", severity=warning|info)
                 │
                 ├─→ /qc 页面问题明细（可只筛 VLM）
                 ├─→ /preprocess 规则 qc_pass      （只认 error，所以 VLM 不会误删）
                 ├─→ /export 规则 qc_pass
                 └─→ 报告文件 storage/reports/qc_*.json（含逐问回答与场景描述）
```

**VLM 结论写进同一张 `qc_findings`，所以下游一行代码都不用改。**

### 红线：VLM 判定**永远不产生 `error`**

`error` 才触发「打回重采」。VLM 会误判，所以它的结论只落 `warning`（待复核）
或 `info`（提示）。**是否删除数据由人决定** —— 这条在 `vlm_selftest.py` 里有断言守着。

## 4. 起后端（三种任选，平台侧代码无需改动）

平台只依赖 **OpenAI 兼容的 `/v1/chat/completions`**（图片走 `image_url`），
所以后端随便换，`storage/vlm_config.json` 改 `base_url` 即可。

### 方案 A · ollama（Windows 上最省事，推荐先跑通）

```powershell
# 1) 装 ollama 后拉模型（Q4 量化，约 3.3GB，8GB 显存够用）
ollama pull qwen3-vl:4b

# 2) 确认服务在跑（默认 11434）
curl http://127.0.0.1:11434/v1/models
```

平台配置（默认值就是这样，通常不用改）：

```json
{ "base_url": "http://127.0.0.1:11434/v1", "model": "qwen3-vl:4b", "api_key": "ollama" }
```

### 方案 B · llama.cpp（llama-server，显存更省、可控性更强）

```powershell
llama-server -m Qwen3-VL-4B-Instruct-Q4_K_M.gguf --mmproj mmproj-Qwen3-VL-4B-f16.gguf `
             -ngl 99 -c 8192 --host 127.0.0.1 --port 8080
```

配置：`{"base_url": "http://127.0.0.1:8080/v1", "model": "qwen3-vl"}`

### 方案 C · 云端 API / 公司内部推理服务

配置 `base_url` + `api_key` + `model` 即可。**注意**：数采数据出网需要先过合规。

> **本机显存提醒**：RTX 5070 Laptop 8GB。Qwen3-VL-4B 的 bf16 权重约 8~9GB，
> **装不下**，必须用量化版（ollama / GGUF Q4 都行，约 3GB）。
> 质检是**离线批处理**，不要求实时，放服务器 4090（24G）跑 bf16 更快更准。

### 离线验证（不需要任何模型）

```powershell

python tools\vlm_mock_server.py --port 8199 --mode mixed
# 然后把 vlm_config.json 的 base_url 指向 http://127.0.0.1:8199/v1

# 或者直接跑自检（自带 mock，不碰真实数据）

```

## 5. 校准：这一步不做，VLM 质检就不能用于打回

VLM 说「这条不合规」听起来很有说服力，但没有校准集，你**回答不了**两个必然被问到的问题：
它报出来的里有多少是真的（查准率）？真的坏样本里漏了多少（查全率）？

### 步骤

```powershell
# ① 生成待标注模板
python tools\vlm_calibrate.py --dataset 1 --dump-template labels.json

# ② 人工把每条 ok 填成 true（合格）/ false（不合格，例如任务没做成）
#    至少 50 条，好坏样本都要有

# ③ 跑校准
python tools\vlm_calibrate.py --dataset 1 --labels labels.json
```

输出（示例格式）：

```
  混淆矩阵   TP=12  FP=3  FN=2  TN=33
  查准率 P   0.800   （VLM 报出来的里有多少是真的）
  查全率 R   0.857   （真的坏样本里抓到了多少）
  F1         0.828
  误报率     0.083   漏报率 0.143

  逐条规则的贡献：
    VLM·任务完成          TP=9  FP=1  FN=1   P 0.900  R 0.900
    VLM·动作成败          TP=3  FP=2  FN=1   P 0.600  R 0.750

  判定口径扫描（至少 N 条警告才算不合格）：
      N      P      R     F1    FP    FN
      1   0.800  0.857  0.828     3     2
      2   0.929  0.643  0.760     1     5
  → 想要少误报就调大 N；想要少漏报就保持 N=1
```

报告同时写入 `storage/reports/vlm_calib_*.json`（含逐条明细，可回溯）。

> ⚠ **样本量 < 30 时指标只作参考**，脚本会自己提示。
> 校准集要覆盖真实坏样本类型，否则算出来的是假的高分。

## 6. 配置项（`storage/vlm_config.json`，页面/接口也能改）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `base_url` | `http://127.0.0.1:11434/v1` | OpenAI 兼容后端 |
| `model` | `qwen3-vl:4b` | 模型名 |
| `api_key` | `ollama` | 云端 API 才需要 |
| `mode` | `both` | `checklist` / `describe` / `both` |
| `frames` | `6` | 每条相机抽几帧（**首帧与末帧必抽**） |
| `tile_width` | `320` | 每格宽度；越小越省显存 |
| `max_tiles` | `12` | 全图最大格数（多相机时摊分） |
| `timeout_s` | `180` | 单次请求超时 |
| `severity` | `warning` | checklist 判不合规的级别 |
| `fail_verdict_severity` | `warning` | describe 判 fail 的级别 |
| `uncertain_severity` | `info` | 判定不确定 / 正反不一致的级别 |
| `emit_description` | `true` | 把描述写进报告（可用于回填语言指令） |
| `use_cache` | `true` | 相同内容不重复问 VLM |
| `checklist` | 4 条 | 预设问题；**改这个不用改代码** |

### 拼图布局

```
列 = 时间（左 → 右，含首帧与末帧）      行 = 相机
┌──────────┬──────────┬──────────┐
│ cam0 f0  │ cam0 f10 │ cam0 f23 │   ← 同一台相机的时序，首末对比
├──────────┼──────────┼──────────┤
│ cam1 f0  │ cam1 f10 │ cam1 f23 │   ← 另一台相机（腕部等）
└──────────┴──────────┴──────────┘
```

每格左上角白字是「相机名 帧号」，提示词里也说明了行列含义。
**首帧 + 末帧 + 均匀抽帧**是判断「有没有做成」最有效的最小集合。

## 7. 缓存与幂等

`vlm_checks` 表按 `(dataset_id, episode_index, model, prompt_hash, content_sha)` 唯一：

- **内容没变**（拼图字节的 sha256 相同）→ 直接复用结论，不再花算力；
- **配置没变**（prompt 指纹含模型、模式、问题清单、抽帧参数）→ 同上；
- 任一变了 → 自动重新问一遍；
- 页面勾「忽略缓存重新问一遍」→ 本次强制重跑。

换句话说：**重复质检同一个数据集不会重复烧 GPU。**
实测（206 条数据集）第二次质检 VLM 部分耗时降到接近 0。

## 9. 局限与红线（如实说明）

1. **VLM 只标记，不删数据。** 它永远不产生 `error`，因此不会自动触发「打回重采」。
2. **没有校准集就不能用于打回。** 拿不到 P/R 之前，结论只能当"参考"。
3. **样本量 < 30 时指标不可靠**，脚本会提示。
4. **4B 模型的能力边界**：4B 适合"任务做没做成、画面能不能用"这类粗粒度判断；
   细粒度（夹爪是否精确套上、螺丝是否拧到位）建议换更大的模型或加专用检测器。
5. **单帧判断能力有限**：只抽帧不做时序推理，快速动作可能看不出来。
   需要时把 `frames` 调大，或改成传视频。
6. **本地 8GB 显存只能跑量化模型**，bf16 必须上服务器。
7. **描述式会产出语言指令，但不是标注**：回填后标记为「由 VLM 生成，待人工确认」，
   人工审核通过后再用于训练。

## 10. 建议的验收标准（第一阶段）

| 项 | 建议目标 |
| --- | --- |
| 校准样本量 | ≥ 50 条，好坏样本都覆盖 |
| 查全率（漏报） | ≥ 0.80（宁可贵一点，别漏坏样本） |
| 查准率（误报） | ≥ 0.60（误报由人工复核消化） |
| 单条耗时 | ≤ 10s（4B 量化 + 6 帧，本机） |
| 缓存命中 | 重复质检时 ≥ 90% |
| 报告可追溯 | 每条结论含逐问回答/描述/耗时/模型名 |
| 红线断言 | `python vlm_selftest.py` 全绿 |

## 11. 常见误解：任务显示「完成」，但 VLM 其实没生效

这是**最容易踩的坑**，第一次用几乎都会遇到。

页面上「🧠 VLM 内容质检」会显示探活状态：

```
● 后端不可达 http://127.0.0.1:11434/v1
```

这时候如果点「▶ 执行 VLM 质检」：

- 任务会**正常走完**并显示「完成」；
- 但每条 episode 只会得到一条 `VLM·服务不可用` 的 **warning**；
- **一个真实的内容判定都不会产生**。

原因是刻意的设计：**VLM 挂了不能让整个质检崩掉**。结构规则（行数/帧数/NaN/时间戳）
必须照常出结论，所以 VLM 那部分失败时只是如实标注"没看成"，而不是让任务失败。

### 怎么区分「真跑了」和「没跑成」

| 看哪里 | 真跑了 | 没跑成 |
| --- | --- | --- |
| 质检记录表的 VLM 列 | `7 条 · 可疑 2` | **`后端不可用·VLM 未生效`**（红色） |
| 问题明细里的规则名 | `VLM·任务完成` 等 | 全是 `VLM·服务不可用` |
| 「VLM 逐条结论」表 | 有逐问回答、场景描述 | **空的**（缓存表 `vlm_checks` 0 行） |
| `/log` 审计 | `VLM 复核 N 条，标出可疑 M 条` | `VLM **未生效**：N 条全部因后端不可用没看成` |
| API 返回的 `summary.vlm` | `effective: true` | **`effective: false` + `warning` 文案** |

现在页面上还有两道拦阻：后端不可达时点「执行」会先弹确认框；
跑完若未生效，消息区会直接标红。

### 修好后怎么重跑

**直接重新质检即可**，缓存不会挡住重跑 —— 因为失败的调用**不会写缓存**
（`vlm_checks` 里不会有「服务不可用」的记录）。

### 顺带一个正确行为

如果之前成功跑过、缓存里有结论，之后后端挂了再跑，平台会**直接复用缓存里的结论**
并报告 `effective: true` —— 这是对的，那些结论确实来自模型。
想强制重新问一遍，勾「忽略缓存重新问一遍」。

## 12. 自检涵盖的内容

`python vlm_selftest.py`（47 项，不需要模型、不碰真实数据）：

- 抽帧拼图：尺寸、首末帧必含、多相机成行、内容指纹
- 两种模式都能单独跑、都能解析
- 全合规不误报 / 全不合规命中 / **VLM 绝不产生 error**
- 正反问不一致 → 降级待人工确认
- 模型输出非 JSON → 走「未取到回答」兜底
- 后端不可用 → 降级为 warning，**绝不抛异常**（结构质检照常完成）
- **后端全程不可用 → 标 `effective=false`，不把「服务不可用」算成可疑**
