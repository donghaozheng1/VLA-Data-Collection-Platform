# 开源机器人数据采集平台调研（2026-10-14）

> 调研问题：**HuggingFace 等开源生态里，有没有现成的"数据采集平台架构"可以借鉴/直接用？**
> 调研结论先说：**有"数据采集工具链 + 数据格式标准"，但几乎没有"完整的采集平台"** —— 平台层（Web + 多用户 + 治理 + 编排）正是我们自己在做的部分，且是行业空缺。

---

## 一、结论速览

| 类型 | 代表项目 | 提供什么 | 是否"平台" |
|---|---|---|---|
| **采集工具链** | **LeRobot**（HuggingFace）| `record`/`teleoperate`/`calibrate`/`replay`/`dataset-viz`/`edit-dataset` 等 CLI + 数据格式 + Hub 集成 | ❌ 库/CLI 级 |
| **数据托管与分发** | **HF Hub / Datasets / Spaces** | 数据集版本、看板、可视化、分发 | ⭕ 托管平台（非采集）|
| **采集范式（硬件标准化）** | **DROID**（13 校联盟）| 统一硬件 + 统一采集脚本 + 中心化数据 | ⭕ 有完整采集 SOP |
| **众包/遥操作采集** | **RoboTurk / RoboMimic**、**ALOHA**、**BridgeData V2** | 采集流程 + 数据格式（HDF5）| ⭕ 流程级 |
| **工厂化大规模采集** | **AgiBot World**（智元）| 工业化采集产线 | ⭕ 有流程，代码部分开源 |
| **合成数据放大** | **MimicGen / RoboCasa / Isaac GR00T** | 少量真机示范 → 物理引擎放大 250×、仿真量产 | ⭕ 管线级 |
| **可视化/调试** | **Rerun**、**Foxglove** | 机器人数据实时可视化 | ❌ 工具 |
| **标注** | **Label Studio**（我们服务器上已部署！）| 通用标注平台，支持多模态 | ⭕ 平台（通用，非机器人专用）|

**最重要的行业事实**（多来源一致）：**采集方式五花八门，但分发格式已经统一到 HuggingFace 的 LeRobot 格式** —— DROID、Open X-Embodiment、GR00T、RoboCasa、LIBERO 全部转成了 LeRobot 格式（见 [Pebblous 六数据集对比](https://blog.pebblous.ai/report/robot-physical-ai-datasets-landscape/en/)）。

> 对我们是好消息：**我们平台的数据契约（LeRobot v2.1/v3.0）已经是行业标准**，不用改。

## 二、HuggingFace 生态（最相关，优先级最高）

### 2.1 LeRobot（github.com/huggingface/lerobot）

它其实是**一整套采集工具链**，不是单一库：

| 命令 | 作用 | 我们的对应功能 |
|---|---|---|
| `lerobot-record` | 采集（遥操作/自主），自动写数据集 | 平台的「采集接入」（我们不做实时采集，走离线导入）|
| `lerobot-teleoperate` | 遥操作（主从臂/游戏手柄）| ❌ 我们没有 |
| `lerobot-calibrate` | 机械臂/相机标定 | ❌ 我们没有 |
| `lerobot-replay` | 回放已采集 episode | ⭕ 我们的「仿真直播-轨迹回放」|
| `lerobot-dataset-viz` | **本地网页可视化数据集** | ⭕ 我们的数据管理/预览页 |
| `lerobot-edit-dataset` | 数据集编辑（删/合并/拆分）| ✅ 我们的**预处理 + 7 个修复算子更强** |
| `lerobot-eval` | 在仿真环境评估策略 | ⭕ 我们的仿真直播 |
| `lerobot-train` | 训练 | ✅ 我们已接入（服务器上跑通 X-VLA）|

**它的架构要点（值得借鉴）**：
- **采集即写标准格式**（边采边写 LeRobot v3.0，无转换环节）
- **Hub 集成**：数据集/模型带版本 tag（`v2.1` / `v3.0`），可 `push_to_hub`
- **相机/机械臂抽象**：`Robot` / `Teleoperator` / `Camera` 三类插件式接口 —— **新硬件只需实现接口**
- **processor pipeline**：pre/post-processor 配置化（我们做 X-VLA 时实际用到了 `policy_preprocessor.json`）

**它没有的（正是平台层）**：
- ❌ Web 平台 / 多用户 / 权限 / 任务编排
- ❌ 数据质检（超出格式层面）/ 修复 / 版本血缘
- ❌ 采集任务管理、采集人员/进度管理
- ❌ 数据的业务语义（场景、任务、采集批次、工件）

### 2.2 HF Hub / Datasets / Spaces

| 能力 | 说明 | 我们能借的 |
|---|---|---|
| **Dataset Viewer** | 网页直接看数据集（含视频帧！）| 我们的数据预览页可对标 |
| **版本 tag**（v2.1/v3.0）| 数据集版本可追溯 | 我们的"版本 + 血缘"思路一致，但我们可以更细（采集批次/质检报告）|
| **Spaces** | 免费托管 Gradio/Streamlit 应用 | 可以把我们的可视化页面做成 Space 分享给领导/合作方 |
| **Xet 存储** | 大文件去重/加速 | 需付费/自建 |

### 2.3 社区生态里可直接用的
- **`IPEC-COMMUNITY/droid_lerobot`**（DROID 的 LeRobot 版，92,233 episodes）—— **现成的大规模预训练数据**，可直接用来做我们的 VLA 预训练
- **`IPEC-COMMUNITY/OpenX-LeRobot`**（OXE 的 LeRobot 版，31 个子集）—— 同上
- **`nvidia/PhysicalAI-Robotics-GR00T-X-Embodiment-Sim`**（~345k 轨迹 / 1.91TB，CC-BY 4.0，**可商用**）

## 三、学术界/工业界的"采集平台架构"范式

### 3.1 DROID —— **硬件标准化的采集范式**（最值得学）

| 维度 | 做法 |
|---|---|
| 硬件 | **统一**：Franka Panda 7-DoF + Robotiq 2F-85 夹爪 + 2×ZED 双目 + 腕部 ZED Mini + Oculus Quest 2 遥操作 |
| 规模 | 76,000 轨迹 / 350 小时 / 86 任务 / **564 场景** / **50 位采集者** / 13 家机构 / 12 个月 |
| 关键设计 | **硬件统一 → 数据天然可比**；相机标定 1,417 个视角全记录；场景"in the wild"（办公室/厨房/走廊）|
| 开放程度 | 代码 Apache-2.0，数据 CC-BY 4.0 |
| **可借鉴** | **"采集硬件 + 采集脚本 + 采集规范三者标准化"** —— 我们的 zhiyan 采集应该照此固定：机械臂型号/相机位置/分辨率/帧率/遥操作方式/SOP + 标定记录 |

### 3.2 Open X-Embodiment / RLDS —— **格式统一的价值**
- 60 个数据集 / 22 种机器人 → 统一到 **RLDS**（TFDS 的机器人子集）→ 训练 RT-1-X 比原模型高 50%，RT-2-X 涌现技能约 3 倍
- **教训**：**把异构数据绑到同一个 loader，价值等同于多采数据**
- 对我们的启发：我们的平台已统一到 LeRobot → 可以像 OXE 一样**把多来源数据（zhiyan/宇树/其他）汇成一个池子做预训练**

### 3.3 其他采集流程范式

| 项目 | 范式 | 特点 |
|---|---|---|
| **RoboTurk / RoboMimic** | 众包遥操作采集 | 手机/浏览器遥操作，HDF5 格式，适合分布式采集 |
| **ALOHA / Mobile ALOHA** | 双臂主从遥操作 | 低成本、高精度；有硬件 BOM + 装配指南 |
| **BridgeData V2** | 低成本 WidowX 采集 | 24 环境 / 13 技能，强调场景多样性 |
| **AgiBot World**（智元）| **工厂化产线采集** | 5 大场景/100 万+ 轨迹级；IROS 2025 AgiBot World Challenge |

### 3.4 合成数据管线（我们的增量方向）

| 项目 | 做法 | 放大倍数 |
|---|---|---|
| **MimicGen**（NVIDIA）| 少量人类示范 → 物理引擎改写场景/物体/机械臂 | ~250×（200 → 50,000+）|
| **RoboCasa** | 120 厨房场景 + MimicGen → 100,000 轨迹 | — |
| **Isaac GR00T** | Isaac Sim 工业级量产 | ~345k 轨迹 / 1.91TB |

> 对我们最有价值的一条：**我们有 zhiyan 的 MuJoCo 模型 + 7 条真机数据** → 可以照 MimicGen 思路**在仿真里放大**（换物体位置/光照/相机），低成本把 7 条扩成几千条。这比"再采几千条真机"便宜几个数量级。

### 3.5 可视化 / 标注工具

| 工具 | 用途 | 现状 |
|---|---|---|
| **Rerun** | 机器人多模态数据实时可视化（时间轴 + 3D + 图像）| 开源，采集调试事实标准 |
| **Foxglove** | 同上（ROS 生态）| 商业 + 开源版 |
| **Label Studio** | 通用标注平台（图像/视频/文本/多模态）| ⭐ **我们服务器上已部署并运行 14 天** |
| **lerobot-dataset-viz** | LeRobot 数据集网页可视化 | 已在我们环境里 |

### 3.6 行业公认的"空缺"：数据溯源（Provenance）

Pebblous 的六数据集对比指出了一个**全场空白**（DROID/OXE/GR00T/RoboCasa/MimicGen/LIBERO 全都缺）：

| 缺失的轴 | 含义 |
|---|---|
| 接触力台账 | 抓取/释放时的力时序（判断任务是否物理成功）|
| 生成血缘 | 合成数据的 seed / 光照 / 初始条件（可复现性）|
| 物理一致性哈希 | 数据是否物理合理的可验证凭证 |
| 失败/丢弃日志 | 采集失败的记录（现在全被丢掉）|

**这对我们是机会**：我们的平台**天生有血缘 + 质检 + 版本**，只要再补上**接触力记录**和**失败日志**，就能在"数据可证明性"这个下一代竞争点上领先。

| 数据质检 | ❌ | ❌ | ⭕（通用）| ⭕（人工）| ✅ **13 条规则** |
| 数据修复 | ⭕ edit-dataset | ❌ | ❌ | ❌ | ✅ **7 个算子** |
| 数据划分/隔离 | ⭕ | ❌ | ❌ | ❌ | ✅ **random/ordered + splits.json** |

| 训练编排 | ⭕ CLI | ❌ | ❌ | ❌ | ✅ **平台任务 + 远程服务器后端** |
| 训练 | ✅ | ❌ | ❌ | ❌ | ✅ **已接 lerobot（含 X-VLA）** |

## 七、对标 [Embodiflow（io-ai.tech）](https://io-ai.tech/platform/guides/)：有开源替代吗？

### 7.1 先说这个平台是什么

**Embodiflow** 是**企业级具身智能数据平台**，覆盖"采集 → 上传 → 标注 → 质检 → 导出 → 训练 → 推理部署"全链路，定位是商业化产品（云端实例 / 私有化部署，工作站版 / K8s 集群版）。

关键设计（值得学的）：

| 维度 | 做法 |
|---|---|
| **数据基准** | **以 ROS 数据模型为基准**，把智元/松灵/睿尔曼等各家数据统一转成 **MCAP** 后再管理 |
| **机型适配** | 内置 **23 款机器人**的可视化模型（双臂/人形/协作臂/移动平台）|
| **质检规则** | 帧率、Topic 连续性、时间同步、丢帧 → 可视化诊断报告（**ROS 录制层质检**）|
| **标注/审核** | 自然语言语义标注 + 相机视角物品标注 + **任务状态机 + 人工二次审核 + 打回返工** |
| **导出** | **12 种格式**（LeRobot / HDF5 / RLDS / MCAP / JSON / CSV …）+ 导出历史与额度 |
| **训练/推理** | 内置 11 个策略模型、PyTorch + JAX、单机/多卡；检查点可部署为推理服务（含边缘离线）|
| **权限** | **6 类角色 × 50 个模块权限键** + IP 白名单 + 操作审计 |
| **架构分层** | 客户端(浏览器 + 机器人端 Agent) / 应用层(REST) / 任务层(队列+Worker) / 计算层(训练+推理) / 存储层(DB+对象存储) / **实时层(WebRTC 网关，远程接管)** |
| 规模 | 25 个功能入口、四大分组（数据 / 模型 / 管理 / 概览）|

**与我们平台的关系**：**架构思路高度重合**（我们都做"治理 + 编排 + 可视化"这一层），差异在：
- 它从 **ROS/MCAP 录制层**切入（真机实时采集 + Agent + WebRTC），我们从**离线数据治理**切入
- 它有**出厂级权限/审计/私有化**，我们有**更强的数据修复（7 算子）+ 划分 + 仿真可视化**

### 7.2 开源对标：**没有整平台，但有能拼出 80% 的组件**

| Embodiflow 能力 | 开源对标 | 成熟度 | 备注 |
|---|---|---|---|
| **数据集策划/可视化管理平台** | ⭐ **FiftyOne (Voxel51)** | 高 | **已原生支持 MCAP + LeRobot**，有插件机制可自写具身数据处理；[官方博客：用 FiftyOne 插件做机器人数据策划](https://voxel51.com/blog/fiftyone-plugins-mcap-lerobot-curation)、[GR00T-X-Embodiment-Sim 原生 MCAP 接入](https://docs.voxel51.com/dataset_zoo/datasets_hf/gr00t_x_embodiment_sim.html) |
| **数据质量验证（质检）** | ⭐ **hflow**（[Hebbian-Robotics/hflow](https://github.com/Hebbian-Robotics/hflow)）| 中（新）| 定位就是"**给机器人团队验证训练数据质量**"的 SDK —— 与我们 13 条质检规则思路一致 |
| 数据格式与训练 | **LeRobot** | 高 | 格式标准 + 训练/评估；**无平台** |
| 标注 + 审核状态机 | **Label Studio**（⭐ 我们服务器上已部署）| 高 | 有任务/角色/审核工作流；**CVAT** 亦可 |
| 可视化 / 回放 | **Rerun**、**Foxglove** | 高 | MCAP 就是 Foxglove 的开源格式（[foxglove/mcap](https://github.com/foxglove/mcap)）|
| ROS 录制 / 格式 | **rosbag2 / rosbags / mcap** | 高 | MCAP 是开放标准 ✓ |
| 数据版本与血缘 | **DVC**、**LakeFS**、Pachyderm | 高 | 对应我们的"版本 + 血缘"，但更偏文件级 |
| 数据质量规则（通用）| **Great Expectations**、Deepchecks | 高 | 通用表格/数据质量，非机器人专用 |
| 训练追踪 / 实验管理 | **MLflow**、**ClearML**（开源核心）| 高 | 对应我们的"实验对比 + 指标" |
| 任务队列 / 编排 | **Airflow / Prefect / Celery + Redis** | 高 | 对应它的"任务层 Worker" |
| 推理服务部署 | **Triton / TorchServe / KServe** | 高 | 对应它的"推理服务 + 边缘部署" |
| 权限 / 审计 | 无现成机器人专用；用**通用 RBAC**（Casbin/OPA）+ 审计日志 | 中 | 它 6 角色 × 50 权限键是产品级打磨 |
| 设备接入 / WebRTC 远控 | **MediaMTX / Janus / LiveKit**（开源）| 高 | WebRTC 网关可开源替代 |
| **整平台** | ❌ **无开源等价物** | — | 见下 |

### 7.3 结论

> **没有任何开源项目直接对标 Embodiflow 这个"整平台"。**
> 但它的**每一层都能找到成熟开源件**，最贴近的是这条组合：
>
> **`FiftyOne`（数据策划/可视化，已支持 MCAP+LeRobot）+ `hflow`（质检）+ `LeRobot`（格式/训练）+ `Label Studio`（标注）+ `Rerun`/`Foxglove`（可视化）+ `DVC/LakeFS`（血缘）+ `MLflow`（实验）+ `Airflow`（编排）+ `Triton`（推理）+ 通用 RBAC（权限）**
>
> 也就是：**开源提供"零件"，商业产品提供"整机"。而"整机"的门槛主要在 —— ① 统一数据契约（ROS→MCAP）② 多机型适配 ③ 角色/权限/审计的产品化打磨 ④ 私有化交付。**

### 7.4 我们平台的位置与建议

| 层 | 开源件能覆盖 | **我们平台现状** | 建议 |
|---|---|---|---|
| 数据契约 | LeRobot / MCAP | ✅ LeRobot v2.1/v3.0 | 可再支持 **MCAP 导入**（对齐 ROS 生态）|
| 机型适配 | 无 | ⭕ 目前 zhiyan + LIBERO | 照 Embodiflow 做"机型库"（我们有 zhiyan URDF）|
| 质检 | hflow / 通用规则 | ✅ **13 条规则**（格式/数据层）| 可补 **ROS 录制层规则**（帧率/Topic/时间同步/丢帧）|
| 修复 | 无（FiftyOne 有基础编辑）| ✅ **7 算子**（我们更强）| 保持优势 |
| 标注 | Label Studio / CVAT | ⭕ 自建（较弱）| **对接 Label Studio**（服务器已部署）+ 审核状态机 |
| 版本血缘 | DVC / LakeFS | ✅ 版本 + 血缘 | 保持 |
| 训练/推理 | LeRobot / MLflow / Triton | ✅ 训练已通；❌ 无推理服务 | 加"检查点→推理服务"（可对标它的 ModelInference）|
| 权限/审计 | 通用 RBAC | ⭕ 简单（admin/user）| 若要多角色协作，需按角色×模块建权限 |
| 实时采集 | MediaMTX / 开源 WebRTC | ❌ | 若走真机实时采集，这是必须补的一块 |

**三条最划算的动作**：
1. **对接 Label Studio**（服务器上现成）→ 补上"标注 + 审核状态机 + 多角色"，这是 Embodiflow 最产品化的一块，也是我们最弱的
2. **接入 FiftyOne 做数据集策划层**（它已支持 MCAP + LeRobot）→ 省掉我们自建可视化/检索/筛选的大量工作，还能白拿它的插件生态
3. **引入 hflow 做质检**（或借鉴其规则集）→ 与我们的 13 条规则合并，形成"格式层 + 录制层"双层质检
